## 실제로 수정한 것 (P1 — 긴급)

### 1. `modeling/skin_rf/predict.py` 라벨 설명 오류
production 라벨은 binary_label_B(EPA I/II/III=양성, IV=음성)인데 예측 결과 메시지는 여전히
"양성=EPA I/II, 음성=EPA III/IV"로 찍고 있었음 — **Category III의 양성/음성이 반대로 출력되는**
실사용자 체감 버그. `predicted_label_meaning`을 "EPA I/II/III 상당" / "EPA IV 상당"으로 수정.

### 2. `cosmetic_validation/skin_irritation_validation.ipynb` resolved_pct KeyError + 정답라벨 오류
- `common_cols`가 `resolved_pct`를 제외하지 않아서 실제로 노트북을 끝까지 실행하면
  `KeyError: 'resolved_pct'`가 남(이전 "0/4 일치"라는 결론은 **실행 안 된 코드의 가상 결과**였음).
  `predict.py`의 `aggregate_formulation`과 동일하게 `resolved_pct`를 common_cols에서 빼고
  `vec["resolved_pct"] = resolved_pct`로 따로 주입하도록 수정.
- 외부검증 정답(`skin_binary`)이 구버전 라벨A(I/II=양성, III/IV=음성) 기준으로 만들어진 상태였는데
  현재 production은 라벨B(I/II/III=양성, IV=음성) — 이 5개 제품 전부 Category III라서 **정답 자체가
  거꾸로 기록**돼 있었음. `cosmetic_validation/flea_tick_shampoo.csv`에 `skin_binary_B`/`eye_binary_B`
  컬럼을 새로 추가(원본 `skin_binary`/`eye_binary`는 라벨A 기준 참고용으로 보존).
- 두 버그를 고치고 노트북을 `jupyter nbconvert --execute --inplace`로 실제 재실행한 결과:
  **일치가 0/4 → 4/4로 완전히 뒤집힘.** (모델이 화장품을 잘 맞힌다는 뜻은 아님 — 해석은 노트북
  결론 셀에 자세히 적어둠: 구조 해결 성분이 여전히 조성의 0.78~3.93%뿐이고 살충보조제 위주라,
  정답과 일치한 게 모델이 계면활성제 완화효과를 이해해서가 아니라 "III급은 원래 거의 다 양성으로
  분류되는 경계급이라 맞추기 쉬웠을 가능성"을 배제 못 함. n=4로 통계적 의미 없음. 결론을
  "이 작은 표본으로는 화장품 적합성을 판단할 수 없다"로 수정.)

## 실제로 수정한 것 (P2)

### 3. `modeling/skin_rf/predict.py` 농도 입력 검증 버그
`float(c.get("amount_pct", 1.0) or 1.0)` — Python에서 `0 or 1.0`은 `1.0`이 되므로 **0%가 1%로
둔갑**하고 있었음(또한 음수/150%처럼 범위 밖 값도 그대로 통과됨). 수정: `None`만 1.0 기본값으로
처리하고, 0은 0 그대로 유지. 유한하지 않거나 0~100 범위 밖이면 명시적으로 `ValueError` 발생시킴.
직접 테스트: 0% → 정상 처리(0.0 유지, 단일성분이라 가중치 0-합 폴백으로 동일 결과), 150% → 즉시
ValueError로 거부됨(이전엔 그대로 예측까지 진행됐음).

### 4. 농도 문자열 파서 `.5%` → `5%` 10배 오류
`세팅/생성스크립트/fix_comp_sig_precision_and_add_concentration.py`와
`skin irritation/rf_feature_compare/rf_et_aggregation_concentration_grid.py`(원자료 파서 동일
코드 2벌)의 `clean_text()`가 끝에 `.lstrip(".")`를 걸어놔서 ".5%"처럼 선행 소수점으로 시작하는
표기를 "5%"로 읽는 버그가 있었음. `NUMBER` 정규식을 `\d+(?:\.\d+)?` → `(?:\d+\.\d+|\.\d+|\d+)`로
바꿔 선행 소수점을 정식으로 허용하고 `lstrip(".")`는 제거(더 이상 필요 없음). **실제 데이터 영향
확인**: 증강 118건의 원자료 3개 파일(`skin_보강후보_통합.xlsx`, `skin_보강후보_v4_신규.xlsx`,
`skin_irritation_최종후보.xlsx`) 전부를 정규식으로 스캔해서 선행 소수점(`.5` 형태) 표기가 실제로는
0건임을 확인함 — **잠재 버그였지만 현재 production 데이터를 오염시키지는 않았음**(재학습/재생성 불필요).

## 확인했지만 당장 안 고친 것 (팀 결정 필요 / 구조적 이슈)

### [P1] 공식 그리드의 OOF 임계값 선택 편향
`rf_et_aggregation_concentration_grid.py`(그리고 원조 격인 `rf_production_recheck.py`도 동일)가
`balance_point(y, oof)`로 **평가에 쓸 바로 그 OOF 예측/정답**에서 threshold를 고른 다음 같은 OOF로
MCC/Sens/Spec을 보고함 — threshold 선택과 성능 평가가 분리돼 있지 않음. 폴드 내부 학습에 test 라벨이
들어간다는 뜻은 아니고, "여러 모델/집계법 중 승자를 고르는" 선택 효과가 수치에 낙관적으로 섞여
들어간다는 뜻. **이건 오늘 처음 생긴 문제가 아니라 11/7 "신뢰할 수 있다"고 확정했던
`RF_production_재검증_보고서`를 포함해 지금까지 모든 공식 재검증이 공유하는 구조적 특성**임
(production `train.py` 자체는 별도 val로 threshold를 정하므로 이 문제와 무관).
→ 올바른 수정은 outer test 봉인 + inner CV로 threshold/모델/집계법을 정하는 nested 평가. 이건
모든 과거 비교의 평가방식을 바꾸는 큰 결정이라 **팀 논의 후 진행**. 지금까지 나온 "wmean이 top을
이긴다", "max가 wmean을 이긴다" 같은 **상대 순위**는 모든 조건에서 동일하게 편향되어 있어서 아마
크게 안 바뀌겠지만, **절대 MCC/Sens/Spec 숫자들은 전부 다소 낙관적으로 부풀려져 있다고 보는 게
안전**함.

### [P1] 공식 CSV 전체 vs 문서 결론 불일치
`skin_official_grid_recheck.csv`에는 (당시 사용자 지시로 추가한) min/max까지 32조건이 들어있고
B/RF/+resolved_pct 기준 **max(MCC 0.302)가 wmean(MCC 0.264)보다 높음** — "wmean이 최종 승자"라는
`진행상황.md` 2026-11-08(5차) 결론은 **32조건 전체 기준으로는 더 이상 사실이 아님**(이미 채팅상으로
사용자에게 보고했던 내용이지만, 문서 파일엔 아직 반영 안 된 상태로 남아있었음 — 다른 팀원이
`진행상황.md`를 수정 중이라 이 파일에 직접 못 쓰고 여기 별도 기록). 단, wmean은 n=659, max/top/min은
n=649라 표본 구성이 다르므로 "숫자만 보고 max로 즉시 교체"하면 안 됨(eye팀 지적 그대로) — 동일
649건·동일 fold·동일 inner threshold로 paired 비교해야 결론 확정 가능. **아직 열려있는 결정**:
wmean 유지 vs max 전환(이전 대화에서 사용자에게 안내한 그대로, 팀 답변 대기 중).

### [P2] baseline(농도 없음) 집계에서 feature가 fold를 넘는 문제
현재 comp_group_id는 농도를 포함해 만든 그룹이라, "+resolved_pct" 비교군은 각 그룹의 feature가
fold를 안 넘지만, 농도를 뺀 "baseline" 비교군에서는 81개 그룹/272행이 동일 feature를 공유하면서
서로 다른 그룹(=서로 다른 fold)에 걸침. baseline 쪽 CV가 완전히 깨끗하지 않다는 뜻 — baseline이
실제보다 좋게 나왔을 수 있고, 그러면 "+resolved_pct"의 개선폭이 실제보다 작아 보였을 가능성(반대
방향은 아님). 농도 다른 제형을 다른 그룹으로 볼지 같은 활성성분군으로 묶을지는 목표 일반화 범위에
달린 정책 결정이라 **팀 논의 필요**(top/min/max 비교에도 동일하게 적용해 민감도 분석 권장).
